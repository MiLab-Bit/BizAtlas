## 三、复赛新增模块（本季度评审重点）

### 3.1 `packages/bizatlas/credit/decision.py` — 贷前审批决策
- **函数**：`build_credit_decision(r, applied_amount, tenor_months)`
- **输出**：`decision`(APPROVE / APPROVE_WITH_CONDITIONS / MANUAL_REVIEW / DECLINE / INSUFFICIENT_DATA)、建议额度上下限、条件清单、担保传染(exposure/chain_depth/dishonest_in_chain)、数据完整度、人工闸门。
- **已测**：3 个 fixture（健康→APPROVE；高风险→DECLINE；失信→命中一票否决 BLACK/DECLINE）。
- **API**：`POST /v1/credit/decision`

### 3.2 `packages/bizatlas/validation/report.py` — 回溯验证
- `load_backtest_report()` 读取 `content/validation/backtest_report.json`
- **反幻觉设计**：报告缺失返回 `available=false` + reason，**不生成占位数字**。
- **API**：`GET /v1/validation/backtest`
- **真实数字**：AUC=0.630(95%CI [0.582,0.676])、KS=0.211；样本 675 条（ST 480 + 非 ST 195）→ 见下「已知局限」。

### 3.3 `packages/bizatlas/compliance/statement.py` — 数据合规自检
- 读 `content/compliance/statement.yaml`，与运行时数据源**逐项对账**
- 自动计算 `reconciliation`(consistent / running_not_declared / declared_not_running)
- **已自动发现并修复**真实偏差：`news_akshare` 运行中但未声明 → 已补进 yaml
- **API**：`GET /v1/compliance/statement`

## 五、当前已知问题与风险点（希望 AI 审查重点提示）

### ⚠️ P0-1：`/v1/analyze` 延迟极慢（~67s）
- **现象**：完整 Agent 流水线（多轮 LLM）+ AKShare 数据拉取导致单次研判 ~67s。
- **怀疑**：`LLM_PROVIDER=openai_compativel` + 微信对话平台 `GLM-5.2` 首token延迟高，或串行调用无并行化。
- **建议请 AI 审**：能否开启 450~850ms LLM 的流式返回 + 多 Agent 并行？AKShare 调用能否缓存？

### ⚠️ 5-2 回溯验证 Recall@ORANGE+=0%
- **因**：本次回测仅喂**财务维度**，事件类否决项（连续亏损/非标审计/失信被执行）未纳入，纯财务梯度下所有 ST 都评 YELLOW。
- **风险**：复赛材料里已诚实披露；但若评委期望「ST 命中率」，需补司法/失信数据源。
- **建议 AI 审**：如何在公开数据下重建「提前预警期」指标？ST 起始年无免费数据源，能否用「连续 2 年扣非净利为负」作为近似标签？

### ⚠️ 5-3 LLM Provider 注册依赖人工
- 当前 `POST /v1/auth/model-providers` 注册的 provider 存 SQLite，但不能重启后自动载入 `.env` 的 `LLM_*` 变量。
- 重启 service 后 provider 仍在（SQLite 持久化），但新增机器初始化脚本不自动引导。
**建议审**：启动时若 SQLite 无 provider 应从 `.env` 自动 seed，避免人工步骤。

### ⚠️ 5-4 服务器资源极低（896MB RAM）
- vite build 触发 Linux OOM Killer（已改为本机构建上传）。
- FastAPI 单 worker + 多数据源拉取 + LLM 调用可能造成内存压力。
**建议审**：可否用异步 + 连接池 / 分页简化？
